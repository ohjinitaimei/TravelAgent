## 这轮验证什么

前几轮分别完成发布 ZIP 校验、空库启动、HTTPS 联调和备份工具测试。本轮将它们串成一条流程：**可信发布包 → 包内生产后端与静态 Web → HTTPS 登录 → 在线快照 → 停服 → 新路径恢复 → 再次登录/数据核对 → 较新快照回退**。

实际使用包内 `backend/`、`deploy/Caddyfile`、`web/`、备份命令和测试进程启动器，而不是开发目录的应用或替换 Provider 的 API。所有 API/Caddy 监听回环地址，私有 CA 只用于这次 HTTP 客户端，TLS 验证保持开启。脚本不会安装系统 CA 或服务。

## 可复现入口

按 README 准备锁定依赖，并按 [发布说明](RELEASE_BACKUP.md) 生成自己的可信归档；Caddy 使用此前校验的官方 2.11.7。

```powershell
.\.venv\Scripts\python.exe scripts/verify_recovery.py artifacts/releases/自己的版本号/TravelAgent.zip --caddy .tmp/tools/caddy/caddy.exe --run-id local-candidate-01
```

当前脚本在原检查上增加完整 A/B 记录（每账号优化行程/调整来源、部分草案和完成收据）恢复核对，并要求归档受检源码与当前一致。新报告只有在服务正常退出和目录清理完成后才通过。

命令会执行包内程序，限于自己构建且来源可信的归档。校验清单和哈希不是来源签名。脚本先校验同一份 ZIP 字节，再将文件解压到本次 `.tmp/recovery-drill-*` 目录，使用当前 Python 依赖环境；不是全新系统的依赖安装验收。

## 实际步骤

1. `tests/recovery_seed.py` 在隔离数据库中离线写入两个 TEST ONLY 账号和各一份测试行程。所有成功 POI/交通样例只来自 tests 中的 FixtureProvider，不是生产数据或生产降级；该过程不向 API 注入测试 Provider。
2. 以发布包中的应用启动 Uvicorn，Caddy 提供同源 HTTPS 与包内静态资源。两个账号分别登录，检查各自只能读到自己的行程，跨账号读取返回 404；额外取得一个测试 Bearer 会话，值只保留在内存中。
3. 测试工具写入一条持久化但未结束的任务，随后调用包内 `travel.backup_schedule` 在线生成第一份已校验快照。该任务是明确的离线测试记录，不能将其解释为真实杀死规划工作进程的测试。
4. 测试工具直接修改源库中的测试标题，API 读回确认变化，再生成第二份较新快照，用于回退。没有通过编辑 API 重算路线，此步骤只验证快照时间点。
5. 文件信号优雅停止本次 API，确认网关 ready 请求返回 502。使用原备份 CLI 将第一份快照恢复到**全新路径**；源库保持原样。
6. 在同一回环上游端口启动恢复库。原 Cookie/Bearer 返回 401，重新登录后行程 ID、第一快照标题和账号隔离保持。未完成任务变为 `failed / backup_restored`、保留收据和显式重试能力，并通过真实 API 事件/SSE 读到恢复终态。
7. 调用恢复后应用创建一个新规划任务。由于本次真实授权已清空，真正的生产 Provider 返回 `provider_not_configured`，任务无行程结果，原行程数量不变。这证明离线测试记录未变成 API 的模拟降级路径。
8. 再次停 API，将第二份快照恢复到另一个新路径后启动。原会话及前一恢复库会话均不能使用；重新登录后读到第二快照标题、相同行程 ID和正确账号归属，前一恢复阶段创建的任务不在该快照中。
9. 核对原源库和两份快照数据库的 SHA-256 未变，复用只读 HTTPS 上线检查验证静态文件、缓存、匿名拒绝、旧 API 关闭及 HTTP 跳转。停止本次所有服务并关闭连接后清理临时目录。

回退同样通过恢复工具生成新库，从而撤销快照中的会话；不会直接重新使用旧数据库的历史会话表。实际业务恢复仍需管理员停服、保留原库并显式选择快照与新路径，不能直接把演练脚本指向个人库。

## 结果与边界

本地完整流程通过 **58 项检查执行**，包含双账号重复核对及最终 HTTPS 检查；报告另外确认全部测试进程退出，且 API/Caddy 均正常停止。归档版本、时间、检查名称、TLS 验证、系统信任未改动和退出状态写入 `artifacts/recovery/report.json`，日志在同目录，全部被 Git 排除。新运行先标记 running，失败写 failed；失败类型和阶段保留，不输出 Cookie、Bearer、密码或业务正文。

本轮增加 3 项种子工具安全回归：拒绝工作区业务库路径、初始写入不覆盖已有测试库、后续阶段拒绝缺失库及未解压的源码位置。定向执行原备份 6、轮换 8、发布包 6 和新增安全 3，共 **23 项 Python 回归通过**。默认 CI 入口增加这 3 项；完整检查集规模因此变为 Python 118、共享客户端 23、浏览器 42 × 3，共 183 个逻辑用例、267 次执行。未在本轮重跑其余全量矩阵。

首次编排在恢复 CLI 的中文输出处因 Windows 默认 GBK 解码而中断，已将子进程明确设为 UTF-8，并区分 JSON 输出和普通状态文本；原备份和生产服务没有修改。HTTPS 启动等待同时确认 CA 和实际 ready 响应，避免仅凭 CA 文件出现就认为入口已就绪。若清理必须强制停止进程，报告不会标成通过。

这 58 项是 TLS HTTP/API 级验收，没有运行真实浏览器交互、配置正式域名/ACME、验证 Linux systemd/timer、安装全新依赖或执行异地备份。种子内容、未结束任务和标题变化均由测试工具离线构造；不是新增真实高德联调或真实任务崩溃演练。现有真实地图与页面矩阵记录保持各自原边界。
