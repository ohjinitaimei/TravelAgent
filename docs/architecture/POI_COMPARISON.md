# 同次真实搜索的地点与路线对比

日期：2026-10-22。对应 [成组优化计划](OPTIMIZATION_PROGRAM.md) A1–A6。实现评价基线、真实备选、预算内联合核验、Web 取舍/定位/原方案编辑、验证隔离及真实多场景对照。继续只在本地交付，复用一个 FastAPI、Provider/MCP 和现有排序/调度；没有核心依赖升级。

## 使用与兼容

新规划可勾选“比较同类备选地点，减少路途”。对应可选严格布尔字段 `PlanRequest.compare_poi_alternatives`，缺省为 `false`。这是用户对有限路线比较的选择，不新增必填输入；旧客户端与旧请求继续原行为，避免悄悄扩大查询成本。自然语言草案应用时重置为 false，工作区只恢复布尔值，不把字符串转换为授权。

开启时从同一次真实搜索（最多 20 个有效地点）保留原排序基线，并最多核验三个额外方案。天数、站数、模式、逐日时段/边界/停留和交通上限不自动更改。评分仍参与原排序，但没有被用户设为硬下限；候选仍须通过现有关键词/类别评分不降低的保护。页面明确可能降低或缺失评分，结果展示实际接口值及未知状态，不能把数值排序当主观体验结论。

只对自动新规划比较地点；编辑继承开关也不会自动替换或跨日搬动用户选择。省略与显式 false 在幂等指纹中等价，true 会参与请求冲突判断。旧行程和旧收据无需迁移。

## 后端流程与判定

1. 既有 `rank_pois(factual_only=True)` 排序。兼容模式取原数量；比较模式保留最多 20 个排序结果，并以原前 N 个作为基线。
2. 在既有 `route_planner.py` 扩展候选：原地理分组、有限单点替换、单日不同最近邻种子、每日单站的日期交换。所有类型合计最多三个，日期和顺序参与去重，地理距离只决定优先核验范围。
3. 原方案中绑定用户费用或逐站停留的地点不被替换；不转移费用，不按同名合并不同 ID。跨日移动按目标日期默认重新调度，逐站覆盖跟随地点。
4. 在外部候选调用前计算基线和已接纳候选的有向路线并集，包含每一天出发/返回。原方案加最多三个同形候选给出保守调用上界，总工具上限仍为 64、候选站间并集仍不超过 48。超额候选在调用前裁剪；共享详情和有向路线在请求内复用。
5. 同一个 `evaluate` 使用真实矩阵、原最近邻排序与原时间调度，生成保存事实；单站有边界时也核验，没有任何交通路段时不额外查路线。
6. 基线可行时，候选须可行，且总交通、最长路段、最忙日总分钟与道路距离不恶化，并至少改善前三项之一；并列稳定选择。基线不可行时，仅接受满足全部时段/交通条件的候选，单列“恢复可行”。没有收益则保留真实可行基线，全部不可行则明确失败。

用户预算金额与费用输入保留；完整预算缺失仍未知，已知超支沿用原警告。这里的 feasible 指时段及交通条件，不代表已确认全部费用、预约、营业或出行体验。已纳入核验的上游调用失败继续使任务明确失败，不以估算或候选省略伪装成功；预算裁剪与上游失败分开记录。失败任务不发出成功的 `selection_validated` 事件。

## 统一摘要与 Web 闭环

新增可空 `Itinerary.planning_comparison`，含基线/采用的真实指标、同任务基线 Day 事实、各已核验候选类型/地点 ID/指标、采用原因、候选数量、预算裁剪与网关逻辑调用数/预留上界。计数不是高德账单。基线可能不可行，只作对照，不是另一可采用的保存版本。

比较模式不再同时输出容易与最终选点冲突的旧 `optimization`；Web 优先展示新摘要，旧记录继续使用原分日对比。OpenAPI 与生成 TS 是双端唯一契约；没有前端路线估算或第二套 Agent。

页面显示交通、最长段、最忙日与道路距离的原值/采用值，逐日移出/加入及真实评分取舍；“定位最长路段”只定位已保存的真实路段。只有采用了候选且基线可行时提供“编辑原方案”：先放入编辑区，用户显式保存后才重新查询路线并创建子版本，不发自动规划请求。来源版本完整保留。

原方案编辑沿用草稿和离线恢复。基线有当前行程未包含的地点时，恢复仍需真实详情核验；失败保留输入，不把旧事实当在线接口成功。草稿只存用户值与 ID，不缓存基线 POI、折线或整个比较摘要。

## 评价与验收工具

`verify_live_quality.py` 仍独立检查来源、方向、时刻、缺项和用户约束，并使用原始基线快照复算基线及采用指标，拒绝缺时间、错 ID、虚假收益、错误候选数量或超预算计数。不可行基线可以仅用于核验对照，不能绕过最终结果的约束检查。

报告分别记录完整性通过、`improved`、`feasible_candidate`、无收益及人工待复核。审计摘要保留原指标/采用指标、原地点与新增/移除地点的实际评分和来源；未知评分不填零。人工评价使用 [复核表](../acceptance/POI_REVIEW_TEMPLATE.md)，没有反馈时保留 `not_assessed`。

新增固定 `practical` 矩阵：

| 场景 | 天数 × 站数 | 方式 | 单任务预留调用上界 |
| --- | --- | --- | ---: |
| 南京公园 | 2 × 2 | 步行 | 17 |
| 杭州公园 | 2 × 3 | 步行 | 49 |
| 苏州博物馆 | 1 × 3 | 驾车 | 25 |

直接 Provider 合计 91；双传输全部执行需 182，会被现有单次 150 预检拒绝。可用 `--scenario` 选择固定场景子集，拒绝未知/重复 ID，不能通过拆运行规避整包预算。

```powershell
.\.venv\Scripts\python.exe scripts/verify_live_quality.py --profile practical --transport direct --date 2026-10-23 --max-provider-calls 91 --dry-run
# 使用自己的合法授权，临时库，实际产生外部调用
.\.venv\Scripts\python.exe scripts/verify_live_quality.py --live-amap --profile practical --transport direct --date 2026-10-23 --max-provider-calls 91 --output artifacts/practical/report.json
```

日期应按实际验证更新。来源/调度通过和词面匹配不等于满意；不能比较两次实时查询的不同路况来归因算法收益，本次收益来自各任务内共享事实的基线/候选。

## 真实验证与收益边界

最终规则的直接 Provider 三场景与南京 MCP 全部通过来源、同任务基线、约束和收益核验：

| 场景 | 原交通 → 采用 | 最长段变化 | 最忙日变化 | 结论 |
| --- | --- | --- | --- | --- |
| 南京两日公园步行 | 73 → 37 分钟 | 减少 31 分钟 | 减少 31 分钟 | 采用候选，减少交通 36 分钟 |
| 杭州两日公园步行 | 279 → 224 分钟 | 保持原值 | 保持 290 分钟 | 采用候选，减少总交通 55 分钟；最长段负担仍需核对 |
| 苏州三站博物馆驾车 | 30 → 30 分钟 | 保持原值 | 保持 120 分钟 | 已核验候选无收益，保留基线 |
| 南京实际 stdio MCP | 73 → 37 分钟 | 减少 31 分钟 | 减少 31 分钟 | 同契约、同一算法，收益独立核验通过 |

同日生产 Web/API 另通过南京站→两日公园→南京南站、逐日时段、编辑默认/显式应用、刷新恢复、保存与来源对照；该有边界样本未获得路途改善，正确保留基线。没有把三城的收益套用到这个不同请求。评分下降/缺失展示与原方案编辑连续流程由隔离生产构建浏览器场景覆盖，不冒充真实用户反馈。

整包预留最多 141 次。先执行的验证与 Web 上界合计 49，诊断搜索 1；最终三城直接调用逻辑数 43、Web 保守上界 25、MCP 11，累计网关调用上界 129，剩余 12 未使用。每次追加阶段先以完整预留上界对剩余额度检查，再以已成功任务逻辑计数或手工编辑保守上界记账，失败则按整阶段预留计入并停止。没有上游失败自动重试，没有扩大 141 次预算；网关计数不替代上游计费账单。

证据在被忽略的 `artifacts/poi-comparison-live/2026-10-22/` 及对应 Web 文件夹，含原始阶段、最终阶段和预算账本，不进入 Git/归档。最终直接调用和 MCP 报告为 `direct-fixed.json`、`mcp-fixed.json`；较早报告保留零收益结果。审计字段后续增加了评分/原地点明细，已有 Web 完整快照可离线重审，不追加 API 调用，也不改写原始执行报告。

## 首次失败与修正范围

- 带默认列表的生成 TS 类型仍可省略，首个构建发现页面直接读取可选 candidates；按契约读取空列表，未手工改生成类型。
- 首个真实阶段全部无收益。一次杭州搜索诊断证明 32 组关键词/类别合格替换被额外的“评分不可下降”条件全部挡住；去掉这个用户未设定的硬条件，保留原排序和相关性门槛，新增评分取舍与显式原方案编辑。
- 控制矩阵先复现每日单站不能换日、全部不可行仍发成功核验事件，再补候选和成功事件时序，未放宽用户条件。
- 浏览器首次分流关键词及后续评分用例的城市标记影响了语义排序。改为与后端相同的评价关键词和不改变语义的隔离测试标记，保留精确收益断言；预算标签含货币符号，修正定位方式，没有加长超时。
- MCP 测试路网最初按 POI ID 判道路，但真实 wire 传坐标；改为坐标驱动，同一事实矩阵 direct/实际 stdio 通过。生产 MCP 传输无需修改。
- 一次完整检查中原有 MCP 超时关闭用例未立即观察到进程退出，原期限/原断言单独复查通过；完整后端复核结果见 [验收记录](../ACCEPTANCE.md)。没有证据确认具体根因，不将它宣称为已定位的生产问题，也未放宽期限或移除断言。

## 测试隔离与发布

`verify_browser.py --run-id <id>` 为每个运行/引擎/套件保留不可覆盖目录 `artifacts/browser-runs/<id>/<engine>/<suite>/`；缺省生成唯一 ID。同范围再次使用已有 ID 在启动服务前拒绝。Playwright report/results 与诊断全部落在独立目录。

执行前用 `--list` 发现计划用例，完成后核对实际 ID 集、每例只执行一次、零跳过/重试及服务优雅退出；`summarize_browser_runs.py --run-id <id>` 要求完整三引擎×三套件，定向执行不能冒充完整验收。CI 同步使用命名空间与汇总，尚未运行 GitHub 云端。

生产新增路径覆盖真实备选/地理绕行/不改善/恢复可行/全失败、输入绑定保护、不同每日时段/起终点/单站换日、最大规模预算、旧请求/收据/记录、API 去重/事件/来源不变、MCP 预算与 direct 对照、独立质量报告。Web 覆盖对比/定位、草稿离线保存、恢复可行、评分取舍/原方案编辑和带基线的十二站性能/存储。完整执行数量及范围以 [ACCEPTANCE.md](../ACCEPTANCE.md) 最终报告为准。
