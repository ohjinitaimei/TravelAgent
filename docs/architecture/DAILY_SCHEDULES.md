# 逐日时段与停留分配

日期：2026-10-22。支持 1–3 天分别设置开始、结束和默认停留，复用原 FastAPI、统一 Provider/MCP、推荐与调度函数。没有新增 Agent、核心依赖或数据库迁移；本轮在本地实现与验收。

## 契约与数据流

`PlanRequest.day_schedules` 是可空的完整数组，按出发日期顺序排列，每项必须提供 `day_start`、`day_end`、`stay_minutes`。非空数组长度须等于 `days`，时刻采用 HH:mm，结束须晚于开始，不支持跨夜；默认停留只接受 10–360 的整数，拒绝布尔值、数字字符串、多余字段和缺字段。

```json
{
  "city": "南京",
  "query": "公园",
  "start_date": "2026-10-23",
  "days": 2,
  "stops_per_day": 1,
  "day_schedules": [
    {"day_start": "08:00", "day_end": "20:00", "stay_minutes": 30},
    {"day_start": "10:00", "day_end": "22:00", "stay_minutes": 45}
  ]
}
```

- 缺省或 `null`：继续使用共用 `day_start`、`day_end` 和 `stay_minutes`。共用字段保留原验证和缺省值，是旧客户端兼容及切回共用的基础。
- 数组模式：每项独立，不继承缺字段，不继承前一天结束时间；有效逐站停留优先级为 `stay_minutes_by_poi[id]` > 当日默认 > 共用默认。
- 编辑省略数组保留来源设置，提供数组整体替换，显式 `null` 清除数组并使用共用设置。编辑不改变天数；新规划可调整天数。
- 空字段从旧提交指纹中规范化去除；数组顺序有业务意义，仍参与幂等冲突判断。
- `Day.schedule` 保存本次实际核验采用的用户时段与当日默认停留；旧记录为 `null`，不重写历史数据。
- 新的逐日超时诊断在每个冲突日期附带原时段和可用分钟；旧共用头字段保留。界面在逐日模式读取行级数据，避免把共用头误当成各天实际时段。

数据流保持 Web / 后续 App → 统一任务 API → 有界工作进程 → 同一 Provider 或 MCP → 既有算法 → 行程与事件存储 → SSE / 轮询。OpenAPI 与生成的 TypeScript 同步更新，移动端可直接提交相同字段，不另建算法。

## 调度与真实数据边界

`backend/travel/schedules.py` 统一解析实际日程和逐站覆盖；原调度函数按当天开始时刻及真实入站分钟计时，真实站间和返程分钟纳入当天结束时限。跨日候选按目标日期重新分配默认停留并核验时段，逐站用户覆盖跟随地点保留，不沿用原日期的默认值。

时段变化没有新增 Provider 入口或交通估算；已有详情/有向路线缓存、有限候选与 64 次工具上限保持。时间或交通不可行仍明确失败，不保存不可行行程，不伪造替代数据。时间诊断复用已查矩阵，不为解释失败追加外部调用。

这些时段及停留是用户安排，不是官方营业/预约时间。费用缺失仍未知；跨夜接驳、房态、真实票价与预约窗口需要另外的可靠授权来源。

## Web 操作与恢复

共用时段和默认停留需先填完整；未完成时切换会保留输入并提示修正，避免隐藏 API 仍需验证的字段。规划表单勾选“按天设置时段与默认停留”，把共用设置复制到各日。可分别修改；增加日期复制共用默认，减少日期只保留对应设置，切回共用采用第 1 天值。界面直接说明切换行为。多日概览展示已保存的实际时段，编辑预览继续注明时间须保存后重算。

编辑已有行程时，逐站停留取自已保存结果。仅修改当日默认不覆盖逐站值；点击“应用到第 N 天站点”才显式批量修改当天，其他日期不变。跨日移动保留该站当前停留，新加站点采用目标日期默认。差异与来源版本对照分别列出当日时段、默认停留及实际逐站变更。

本机草稿允许暂存空时间、无效先后关系或尚未填完的默认停留，恢复后供用户修正；提交时严格验证。草稿只保留用户输入和地点 ID，拒绝嵌入 Provider 事实，旧 v1 缺字段规范化为 `null`。刷新、离线提交恢复、原版本核对和账号隔离沿用现有流程。超时建议按钮定位实际冲突日期的结束或停留输入，不自动改值或提交。
