# 出发地与返回地接入设计

日期：2026-10-22。本文确定下一模块的实现边界，不代表当前 API 已接收这些字段。当前每日时段仍仅覆盖首站至末站的停留与站间交通，Web 使用方式见 [使用手册](../USER_GUIDE.md)。本轮不在表单加入无法执行的选项。

## 首批能力与请求契约

先支持 **单日、1–4 个游览站点、可选出发 POI 与可选返回 POI**；继续使用同一个后端、Provider/MCP 和现有排序/调度。后续多日扩展需先解决完整预算和版本展示，不能直接沿用旧调用上限。

拟在 `PlanRequest` / `EditRequest` 增加 `day_origin_poi_id`、`day_destination_poi_id` 两个可空 ID，长度沿用现有 POI ID 限制。未提供时完整保持原行为；编辑时“未提供”表示保留，显式 `null` 表示清除，与预算字段同样区分。首批对多日携带非空起终点明确返回统一 422，不忽略字段或部分执行。

用户从授权 POI 搜索中选择地点，不能由 LLM 将“酒店附近”猜成坐标。后端每次任务重新获取起终点详情，与该任务已有 POI 按 ID 复用，最多额外两次详情调用。当前 `/routes` 可接受用户坐标，但首批规划接口先使用 POI ID，避免在选择、草稿和已保存事实之间混淆名称与位置来源。自由坐标后续仍须明确 `user_input` 来源。

起终点不计入每天游览站数，没有默认停留或门票费用。出发和返回可选同一 ID，也可与某个游览站点同 ID；只有连续端点同 ID 时不需额外路段，不能生成标为高德来源的“0 分钟”伪路段。不同 ID 不能仅因名称/坐标接近而当作同地点。

## 路线与调度

有出发地时，`day_start` 表示离开出发地，首站到达为开始时间加真实入站交通；有返回地时，末站结束加真实返回交通必须不晚于 `day_end`。未选的一侧沿用原语义。Web 须在选择控件和约束结果中说明这一区别。

- 在既有 `route_planner._optimize_order_by_distance` 中扩展可选起点距离函数，按真实有向入站距离确定首站，再复用最近邻；不在前端或另一 Agent 复制算法。
- 保留用户顺序时不重新排序，仍核验真实出发/返回路段；返回边界参与可行性，不承诺最近邻能找到所有可行排列或全局最优路线。
- 复用原调度器，以加上入站交通后的首站开始时间排停留与站间交通，再核对返程到达。不得把直线距离、LLM 或接口失败后的估算填进交通矩阵。
- 任意必要详情/路线缺失、超时或拒绝时明确失败，原版本及编辑输入保留。取消与任务期限沿用原任务生命周期，不新增阻塞 HTTP 路径。
- 不可行诊断增加出发交通、站间交通、停留、返回交通分项；显示原始失败方案，不静默删站或缩短用户停留。

拟为 `Day` 增加可空的起终点 POI、边界路段与返回到达时间；`Stop.travel_to_next` 继续仅表示游览站之间的路段，不能把返程塞到末站的该字段而破坏旧客户端语义。详情与路段保留原来源/获取时间。原 JSON 缺新字段按空值读取，不回填假的地点或历史时间，不要求重写旧记录。

## 调用预算与多日门槛

单日最多 4 站，以完整有向站间矩阵和两侧候选边界计算保守上限：

| 操作 | 搜索/详情上限 | 路线数上限 | 合计 |
| --- | ---: | ---: | ---: |
| 新规划 | 1 次搜索 + 2 次边界详情 | 12 站间 + 4 入站 + 4 返回 | 23 |
| 编辑重算 | 4 次站点详情 + 2 次边界详情 | 同上 | 26 |

该上限满足当前 MCP 默认每任务 64 次调用，不需提高核心限额；总时限与任务超时仍单独生效。指向同 ID 的详情和有向路线在任务内复用，实际调用可少于上限；A→B 与 B→A 不能共用事实。

多日最多 12 站时，旧站间候选上限 48 加两侧最多 24 条边界路线，新规划加搜索/边界详情最坏为 75，编辑加站点/边界详情最坏为 86，**超过当前默认 64**。下一阶段必须选择并验证总预算内的候选裁剪或显式有限能力，联动 `propose_day_group_candidates`、MCP 限额与真实验收预检。不得在没有测试时提高默认预算，或继续用旧 49 次上限声称覆盖起终点。

## 保存、展示和兼容

- 已保存行程仍不可变；修改起终点生成关联原 ID 的调整版本。请求去重和提交收据纳入两个新字段，离线恢复沿用同一请求快照。
- 生成 OpenAPI 与双端 TypeScript 类型；旧无起终点请求继续成功，旧版本按空值显示“未设置”。不引入第二套移动端业务算法。
- 编辑差异、草稿校验/版本兼容、版本对照和地图预览必须包含起终点选择；草稿仅保存用户 ID，不缓存 Provider 事实。换号、来源失效和多标签冲突沿用现有保护。
- 地图与时间轴分别显示入站和返程，不把边界 POI 当作游览站。总交通与站间/边界交通分开，更新多日概览、`versionMetrics`、比较表及质量验收器，避免只合计 `travel_to_next` 而漏算。
- 边界交通费用未知时加入预算缺项；不使用公里数推算车费或把驾车收费等同于完整交通成本。

## 实施顺序与验收

1. Schema 与后端：增量字段、统一错误、详情/路线复用、原算法适配、边界调度和预算分项。先用明确 TEST ONLY 输入验证非对称交通、返程单独超时、同 ID 连续边界、必要路线缺失、取消/期限、账号隔离及旧版本读取。
2. Web 与共享客户端：生成类型，增加搜索选择/清除、编辑差异、草稿恢复、地图/时间轴与版本对照。三引擎验证无起终点旧流程、起终点新流程、离线同一提交恢复和未保存保护。
3. 授权实测：先预检任务上限，再用独立库验证单日新规划/调整、返程失败与原记录不变。直接 Provider/MCP 分开记录实际运行范围，不使用模型估算路段。
4. 单日验收通过后再扩展多日与更细交通偏好。最长步行限制、预约时间窗和主观推荐质量仍各有独立输入及数据需求，不把起终点接入视作同时完成这些能力。
