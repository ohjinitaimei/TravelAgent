# 关键词与站数质量矩阵

日期：2026-10-21。本轮扩展可复现的真实数据验收脚本，完成 3 个场景各一次直接 Provider/MCP 规划。沿用同一个生产 API、Provider、排序/分日/调度和任务系统；没有改动生产算法、Web、共享契约或依赖，没有上传 GitHub。

## 运行方式与调用预算

`scripts/verify_live_quality.py` 保留原默认 `smoke`：南京/苏州公园、各 2 天 2 站，直接/MCP 共 4 任务，最多 52 次 Provider 调用。新增 `expanded`：

| 场景 | 关键词 | 天数 × 每天站数 | 交通 | 每传输调用上限 |
| --- | --- | --- | --- | ---: |
| 南京 | 博物馆 | 1 × 3 | 步行 | 7 |
| 苏州 | 咖啡 | 1 × 4 | 驾车 | 13 |
| 苏州 | 公园 | 3 × 4 | 驾车 | 49 |

两种传输共 6 个任务，上限 138 次。每个任务一次搜索；单日为既有完整有向矩阵上限，多日按既有候选矩阵并集不超过 48 条计。上限不是实测网络计数或人民币费用；计费取决于账号授权和套餐。

先安装根 README 中后端及可选 MCP 依赖，再执行无凭证预检：

```powershell
# Windows 重定向 JSON 时固定 UTF-8。
$env:PYTHONIOENCODING = 'utf-8'
.\.venv\Scripts\python.exe scripts/verify_live_quality.py --profile expanded --date 2026-10-22 --dry-run
```

`--dry-run` 只打印固定场景和上限，不读取凭证、不启动 API、不调用地图。实际验收必须显式启用，并配置自己的合法高德 Web 服务 Key：

```powershell
.\.venv\Scripts\python.exe scripts/verify_live_quality.py --live-amap --profile expanded --date 2026-10-22 --max-provider-calls 138 --output artifacts/expanded-quality/report.json
```

可用 `--transport direct` 或 `--transport mcp` 单独运行，扩展矩阵上限为 69。预算不足会在读取凭证/启动服务前拒绝，例如双传输扩展矩阵加 `--max-provider-calls 100`。脚本总上限参数只允许 1–150，固定场景最多 138；没有任意场景文件、自动改条件或业务重试。

每种传输使用自己的临时库，启动回环生产 API，经真实任务创建、轮询、行程和事件查询验收。只连接高德官方地址，不替换 Provider、不调用模型；终止信号关闭服务后清理临时库。非零退出码也记为服务退出检查失败。输出仅允许在忽略的 `artifacts/`，凭证与地图 SDK 安全密钥不写入报告。

## 报告判定

成功任务核对共享 Schema、请求、日期、站数/唯一 ID、真实来源与原始获取时间、缺失标记、路线关联/模式/几何、逐站时间衔接、每日结束及未知预算。单日不要求跨日优化信息，多日核对后端优化指标与实际行程一致。

修复了旧验收器的一个盲点：Pydantic 的 Source 默认值可能在响应缺少获取时间时补上当前时间。现在必须在原响应中存在该字段，不能靠模型默认值制造来源证据。这是验收器的拒绝门槛，生产返回的获取时间与算法未改。

报告分别记录任务成功、任务失败、状态未知、成功任务被验收器拒绝的数量；失败不会变成成功或替代行程。可获取的失败还记录无部分行程、错误码、可重试状态和时间诊断。`passed` 的范围明确为来源/契约/调度检查，不等于主观推荐质量通过。

名称或高德分类包含关键词的数量、未命中 ID、城市字段差异/缺失和原 POI 证据供人工复核。它们是字面匹配线索，不是语义评分、推荐准确率或营业保证；不自动删除真实记录，也不作为生产推荐的新规则。两种传输另比较地点顺序和交通汇总；时点不同导致数据变化时会保留差异，不强制伪装一致。

有跨日优化指标时报告 `route_queries` 的后端矩阵计数。单日没有该计数字段，保持 `null` 并标明 `upper_bound_only`；不会把上限当成实测。优化收益直接取原/结果指标差，未采用分日候选时不虚构收益。
