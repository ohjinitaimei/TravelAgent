# 单日起终点与真实往返调度

日期：2026-10-22。新增可选出发地、返回地的后端契约与 Web 操作，复用同一个 Provider/MCP、推荐函数、最近邻排序和时间调度器；没有新增 Agent 系统或前端路线算法。原 Flutter、核心依赖与数据库表结构未改，仅在本地开发。

## 使用方式

1. 将旅行天数设为 1，在目的地城市中搜索“出发地”与“返回地”，从真实结果中选择。两侧都可不选，或只选一侧；文字本身不会被当作坐标。
2. 选了出发地后，“每日开始”表示离开该地；选了返回地后，“每日结束”表示最晚抵达返回地。起终点不算游览站，没有默认停留或票价。
3. 开始规划后，时间轴分别显示出发、游览站和返回；独立位置的地图标记用“出”“返”与游览编号区分；同 ID 复用标记，地图列表仍分别显示角色并可定位。未配置 JS SDK 时仍可读时间轴与列表。
4. 多日概览、版本对照分别显示站间交通、出发/返回交通和总交通，距离包含已选边界。缺必要路段时展示未知，不按 0 汇总。
5. 编辑时可重新搜索、选择或清除。预览只显示地点，保存后后端重新核验路线，生成新版本；原版本保持不变。草稿、差异、离开保护、离线同一提交恢复均包含所选 ID。

首批支持单日 1–4 站、步行/驾车。多日携带起终点会明确拒绝；切换为多日后需显式清除选择。未选的一侧不计入往返，其他未安排的餐饮、预约等待和未来营业状态也未验证。

## 增量 API

`POST /api/v1/travel/tasks` 在原 `PlanRequest` 增加两个可空字段：

```json
{
  "day_origin_poi_id": "用户从授权搜索中选择的 POI ID",
  "day_destination_poi_id": null
}
```

示例仅演示增量字段，不是可提交的完整请求或真实 POI。合法 ID 长度 1–100，不接受空白；字段省略/`null` 保持无对应边界，非空字段要求 `days=1`。旧字段、任务 202 响应、查询/事件/取消路径均不变。

`POST /itineraries/{id}/adjust` 同样增加这两个字段：省略表示继承来源，显式 `null` 表示清除。合并后的完整请求再经 `PlanRequest` 校验，非法组合返回统一 422，来源版本不改写。提交去重纳入非空新字段；新字段为 `null` 时从任务指纹中省略，以兼容升级前已保存的收据。没有删改旧指纹或绕过请求冲突保护。

`Day` 增加以下可空字段：

| 字段 | 含义 |
| --- | --- |
| `origin_poi` / `destination_poi` | 本任务核验过的出发/返回 POI，含来源、获取时间与缺失标记 |
| `origin_segment` | 出发地 → 首站的真实有向路线 |
| `destination_segment` | 末站 → 返回地的真实有向路线 |
| `origin_departure_time` | 有出发地时为用户每日开始时间 |
| `return_arrival_time` | 有返回地时的实际调度抵达时间，即使与末站同 ID 也保留时间 |

`Stop.travel_to_next` 仍只表示游览站间路线；末站不塞入返程。连续端点同 ID 时，对应 Segment 为 `null`，而不是虚构一条高德来源的 0 分钟路线；不同 ID 不因名称或坐标相似就合并。

历史行程缺新字段时按空值读取，不补历史地点和获取时间。单日 `optimization` 仍为空；是否包含边界交通应读取 Day 字段，不能用跨日优化字段缺省判断。OpenAPI 与 TypeScript 类型已同步生成，移动端未来可复用相同字段和轮询服务。

## 算法、失败与预算

新规划先调用真实搜索与原推荐函数，再核对起终点。已取得的 POI 按 ID 在任务内复用，其他起终点调用详情；编辑先核对已有站点，再复用相同缓存。

`route_planner._optimize_order_by_distance` 增加可选真实入站距离函数，以此选首站，再运行原最近邻。未传该函数时仍以推荐列表第一站起步；手动保持顺序时不重新排序。返程参与可行性检查，但不声称最近邻能找出所有可行方案或全局最优。

原 `_build_route_stops` 增加可选绝对开始分钟，将入站交通加到首站调度起点；结束检查再加返回交通。超长路段也以绝对分钟核验，不因时钟显示绕回次日而误判可行。请求时限、进程取消与工具预算沿用既有机制，API 请求不等待规划计算。

时间失败诊断的 `travel_minutes` 继续表示站间交通，新增 `origin_travel_minutes`、`destination_travel_minutes`（旧诊断缺省为 0）：

`required_minutes = stay_minutes + travel_minutes + origin_travel_minutes + destination_travel_minutes`

任何必要详情、路线、几何或授权缺失均明确失败；取消/超时不保存部分行程。已选边界交通加入费用未知项，不按距离推算车费，不把人均消费当票价。

| 单日最多 4 站 | 详情/搜索上限 | 真实有向路线数上限 | 合计 |
| --- | ---: | ---: | ---: |
| 新规划 | 搜索 1 + 边界详情 2 | 站间 12 + 入站 4 + 返回 4 | 23 |
| 编辑重算 | 站点详情 4 + 边界详情 2 | 同上 | 26 |

这些是结构性上限，不是实测账单计数。相同 ID 与相同有向路段在任务内复用，A→B 与 B→A 分开。MCP 默认 64 次和各项时限保持不变；多日最坏 75/86 次超过默认预算，因此没有直接开放。

## 草稿与启动恢复

草稿仍使用 v1 键，增量保存两个用户选择的 ID，不保存 POI/路线事实。旧 v1 草稿未包含新键时规范化为空值，再与来源版本核对；未知版本、非法 ID、多日起终点组合仍拒绝恢复。恢复前重新读取来源，新增地点仍重新核验。

本轮还修复了启动同步与手动草稿恢复之间的竞争：页面此前在读取历史任务前提前清除 `restoring`，使恢复按钮短暂启用，点击可能被后续同步打断。现在整个同步完成或失败后才解除状态，联网事件也不在启动同步期间重复恢复。确定性测试阻塞任务 GET，先确认恢复按钮保持禁用，释放后再恢复草稿。

## 真实 Web 与 MCP 联调

生产 API/Web、授权高德、独立临时库，出发日 2026-10-23，南京公园 1 天 2 站，每站 30 分钟、步行、09:00–22:00。从授权搜索中选择南京站出发、南京南站返回，结果如下：

| 项目 | 实测 |
| --- | --- |
| 出发 / 站间 / 返回交通 | 44 / 21 / 159 分钟，合计 224 分钟 |
| 停留与总时段 | 停留 60 分钟，总需 284 分钟，13:44 抵达返回地 |
| Web 编辑 | 清除返回地，刷新后显式恢复草稿，断网发送失败后按同一提交恢复，成功创建子版本 |
| 保存对照 | 两版本的总交通及返回地差异可读，原行程不变 |
| 返程失败 | 对原版本显式重算，结束设为末站离开时间 11:05；已排停留/入站/站间刚好占 125 分钟，另需返回 159 分钟，任务失败且超出 159 分钟，无部分行程 |
| MCP | 独立生产 API、同一请求及工具层通过；来源、原始获取时间、边界关联、返回时刻均由质量验收器核对，单次 18.94 秒 |
| 缺失数据 | MCP 样本两站均缺人均消费与营业时间，完整预算未知；不生成门票、未来营业或评论 |

完整通过的这次运行按浏览器 POI REST 读取最多 14 次、直接任务最多 9 + 7 + 10 次、MCP 任务最多 9 次，合计上限 49。浏览器实际记录 7 次 POI 读取尝试，其中一次返回 `429 tool_busy`；页面保留所选 ID 并显示错误，后端重算重新核验成功，没有用模拟结果降级。该结果说明最终业务链路和错误保留可用，不表示每次辅助详情读取均成功。

前两次真实运行停在草稿恢复，各未受理调整任务，保守上限分别为 15；连同最后完整运行，累计上限 79。这是结构性调用预算，不是外部账单计数。没有自动重试业务任务；修复竞争后才显式复验。三次运行均关闭临时服务并清理独立运行库，密钥与运行产物不提交。

本轮不加载真实 JS SDK，截图中的地图为 SDK 未配置状态，不能据此声称已验证新边界标记的真实底图渲染。地图列表/联动由三引擎自动验证；已有真实 SDK 历史记录保留原范围。本轮也未调用模型，未重跑 HTTPS、灾备演练、读屏人工听读或真机。
