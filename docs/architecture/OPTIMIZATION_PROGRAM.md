# TravelAgent 成组优化与验收计划

日期：2026-10-22。设计基线为本地提交 `d444bf3`。本文依据当前生产 Web、统一后端、契约及实际验收记录制定；下文保留 A/B/C 的设计目标；A 包现已成组实现并验收，B/C 是后续工作。后续以完整交付包推进，内部可分提交，不把每个控件或一条测试单独作为一轮交付。

## 目标与当前判断

目标是把已有的数据真实、状态可靠、支持编辑的 Web 工作台，进一步提升为能解释推荐取舍、减少无效路途、完成连续使用流程的可验收产品。继续先做 Web，保留 Flutter，移动端作为后续同后端客户端。

当前已有：统一异步 API、真实高德 Provider/可选 MCP、关键词排序、有限跨日分组、真实道路核验、逐日时段/起终点、交通上限、来源标记、预算缺项、草稿/断网恢复、版本对照、账号隔离及本地部署恢复工具。`d444bf3` 的验收记录为 Python 227、TS 46、三引擎 231 次，即 350 个逻辑用例 / 504 次执行，归档另有 4 项独立启动检查。这些是既有基线，不算本计划的新验收。

当前最明显的产品差距是实用性，而非接口数量：南京两日样本每日全部交通为 215/224 分钟，停留为 30/45 分钟；更早杭州样本最长步行段为 160 分钟。系统会提示且时段可行，但这不能证明安排适合用户。

### 代码证据与约束

## A：六项工作组成一次完整优化

### A1. 先固定评价方法和对照基线

复用 `verify_live_quality.py`，把来源完整性、时段/交通约束、客观路线收益、人工实用性复核分开记录。

- 每天记录停留、入站/站间/返回交通、最长段、交通占比、剩余时段及负担差；单位和缺项语义固定。
- 记录搜索候选数、参与核验候选数、因预算未核验数、采用/保留原因；额度是预留上界，不假装成上游账单。
- 新算法与基线尽量在同一任务中共享相同时间点的真实有向路线事实，不能拿两次实时查询的不同路况直接归因于算法改善。
- 离线回归使用明确 TEST ONLY 的控制矩阵；合法来源记录仅在权限允许时用于本地验证，不当生产降级、不作为公开 POI 数据集。
- 真实矩阵固定场景及预算后执行，不用反复换城市/关键词挑出好看的结果。

产物：版本化场景定义、机器可读对照报告、人工核对表。先定义判定再改算法，记录无法比较和数据缺失，不能自动生成满意度。

### A2. 将未入选的真实 POI 纳入少量替换候选

继续使用现有 `factual_only` 排序结果、地理距离候选函数和同一次 Provider 搜索。保留原基线选点；在后端扩展现有候选接口，允许有限单点替换、已有跨日交换及不同起点顺序，统一去重。

- 备选池不超过当前单次搜索返回上限，候选方案总数先保持最多 3 个，包含所有类型，不能每层各扩 3 个形成组合爆炸。
- 保持天数、每天站数、城市、用户逐日起终点、停留覆盖、交通模式与硬约束；不通过删站、缩短停留、换模式来制造收益。
- 替换受已有可核验的关键词/类别相关性约束，不把仅名称相似当语义真值。初版优先同等相关性的备选；真实评分仅在可用时参与原排序，缺评分不补齐，不引入未授权评论或 UGC 信号。
- 用户指定的编辑分日与已选地点不自动替换或跨日移动；只对自动新规划启用选点候选。基线已选地点绑定了用户费用或逐站停留时，本批保护该地点不被替换；未入选键沿用既有处理，不将费用或停留转给另一地点。
- 同名不同 ID 保留，名称相同不自动合并。选中地点在同一行程中仍不得重复。
- 单日/单站有起终点时可比较实际往返；没有任何交通路段时不为“优化”额外调用路线。

产物：对既有排序/候选模块的有界扩展，保留旧调用方式和既有算法；不另建推荐服务或 Agent。

### A3. 在同一预算下用真实路线做联合核验

候选只提出 ID 和排列，地理距离用于筛候选。真实路程、时间、可行性全部走现有 Provider/MCP 和同一个调度函数。

- 先算原方案和拟接受候选的唯一详情与有向路线并集，预留全部日边界，再在 64 次工具/48 条候选站间约束内接纳候选。超过额度的候选在调用前裁剪。
- 原方案已可行时，候选只有在相关性保护及全部硬约束成立，且总交通、最长真实路段和最忙日总分钟不恶化，并至少一项严格改善时才采用。道路距离也保留既有不恶化保护。
- 原方案不可行时，可以采用满足全部用户条件的候选；须标记为“恢复可行”，不能声称它在所有质量指标上都改善。
- 并列时按稳定顺序/ID 决定，保证控制矩阵可复现；不引入无界随机搜索。
- 没有更好且已核验的候选时保留真实可行基线，说明未发现改善；没有任何可行方案时继续明确失败。
- 若已决定核验的必需真实数据调用失败，保留显式错误与失败状态；不能填估算，也不能把该候选标成已验证。额度裁剪与真实上游失败必须区分。
- 新候选复用现有有向事实缓存，跨日移动重新计算目标日默认停留；结果与报告从同一采用方案产生。

产物：一致的候选准入、判定与原因代码，调用计数可核对，旧有上限/取消/超时不变。

### A4. 同步 API 契约与 Web 的结果解释

不预设新增必填请求字段，不让用户为算法内部参数填表。设计新增可空 `Itinerary.planning_comparison`（名称在实现前定稿），描述同任务的基线、采用结果、候选范围、地点变化及可核对的指标。

- 后端 Schema 为唯一事实源，再生成 OpenAPI/TS；不得手写另一份前端模型。旧请求、旧记录、旧收据与只读版本保持兼容。
- 若只是既有分日交换，旧 `optimization` 可继续成立；若换了 POI 集合，不能让旧 `GroupingOptimization` 冒充最终路线的分日收益。新摘要作为权威展示，必要时旧摘要留空；前端不得同时展示两套相互冲突的结果。
- 用户看到“为什么更合适/为何没调整”、换了哪些站、总交通/最长段/最忙日变化及未核验项。数值由后端给出，前端只展示保存事实。
- 调整页面保留用户值、地图地点预览、离开保护、草稿与离线恢复。没有自动改变已保存行程，也不默认触发新的付费重算。
- 提供定位到负担较重日期和对应路段的操作；修改模式/上限/地点仍是显式新任务，保留来源版本。
- 未核验的营业、预约、价格和完整预算继续明确未知，不为“完整度”填数据。

产物：同一契约、PC 结果解释和兼容展示，整个流程不需要另一套前端路线算法。

### A5. 让预算、结果一致性和跨端恢复可自动验收

在既有测试与验证编排上增加有意义的场景，不以用例数作为质量目标。

- 单日、多日单站/多站、逐日不同边界/时段、跨日默认与逐站覆盖；候选优于/等于/差于基线、原不可行候选恢复、所有候选不可行。
- 坐标接近但道路绕行、方向不对称、同名不同 ID、搜索不足、缺评分和真实工具失败。
- 最大 12 站、边界并集超额、候选被裁剪、缓存不重复调用，以及 direct/MCP 共用算法与相同契约。
- 新旧摘要读取、保存/恢复/来源对照、受理去重、账号隔离；Web 端到端等待真实任务终态。
- 测试进程/结果目录增加运行命名空间或同引擎锁，防止重叠测试清理别人的 trace；报告汇总验证计划数量、终态、重试/跳过、退出与产物来源。
- 复用原性能门槛和任务期限；若出现异常先定位原因，不通过加等待时间或跳过用例达标。

产物：完整回归与新路径测试、可追溯报告汇总、可靠的验证进程隔离；不要求每次文档修改重跑付费验证。

### A6. 真实多场景对照、验收说明与本地交付

优先三类问题场景：南京含车站的两日步行、杭州分散公园步行、苏州/北京的驾车多站；覆盖逐日时段和起终点。日期由实际运行日确定，先 dry-run 预检，再按有界矩阵执行。

- 沿用当前验收工具单次运行不超过 150 次预留调用的限制。整包先编制所有运行的合计预算；不足时在调用前缩小预定矩阵并说明覆盖，不能拆成多个小运行规避总预算。
- 先做直接 Provider 代表性场景；同契约选少量 MCP 对照，不为排列组合重复付费。界面 POI 读取及失败尝试计入计划，失败记录保留，不自动重试挑样本。
- 不同实时请求的数据不能据数值不等宣称传输不一致；比较来源、约束和计算关系，精确算法对照使用同任务事实。
- 真实场景没有收益时诚实记录“不足以证明改善”，结合受控矩阵检查原因；不能把接口成功率当成优化收益。若优化目标没有被证据支持，回到规则/候选设计，保留已通过基线。
- 最终验证 Schema、三浏览器完整路径、来源与工具边界、发布清单/密钥排除、归档独立启动。真实 SDK、模型或灾备只有实际重跑才计入本次验证。

产物：一个可复查的整包验收说明、机器报告、本地提交与发布归档；原记录与失败证据保留，业务数据和凭证不进入 GitHub。

## A 包验收门槛

| 维度 | 必须满足 | 不能用来替代验收 |
| --- | --- | --- |
| 数据真实 | 保存的每条必需路线和 POI 有真实来源；缺失明确处理 | LLM 补路线、模拟价格、测试矩阵混入生产 |
| 约束与兼容 | 已选天数/站数/时段/停留/模式/边界及用户上限成立，旧版本/收据可读，编辑原版不变 | 自动减站、改出行方式、放宽上限 |
| 实用性 | 预设受控问题矩阵证明候选替换确实能改善；每次标成改善都可由同任务事实复算，真实场景分别报告收益/无收益/无法比较 | 仅增加报告、提高接口成功率或笼统宣称“更智能” |
| 资源与失败 | 候选调用前预检，64 次/原时限内，失败/取消可终结；原方案可用不依赖非法降级 | 抬高额度、后台自动反复规划 |
| 产品流程 | 从创建、解释、定位问题、显式调整到保存/刷新/来源对照连贯通过 | 只有独立组件截图或后端单测 |
| 发布 | 新增路径和原回归通过，归档启动与密钥排除验证，报告可追溯 | 用旧报告宣称本次全部通过 |

人工复核建议按“主题是否符合、交通能否接受、安排是否愿意照做、哪些信息不足”记录真实使用者回答。没有回答时保留未评估，不生成主观得分。

## B：需求确认与 Web 连续使用整合

B 包已按以下四项成组实现，契约、操作与验收范围见 [REQUIREMENTS_WORKFLOW.md](REQUIREMENTS_WORKFLOW.md)：

1. **需求草案覆盖实际约束**：将当前逐日时段、停留和交通偏好纳入同一后端草案/澄清契约与确认流程。LLM 只提取用户表达；地点需真实搜索选定，模糊日期/起终点/冲突条件先确认。不要新增一个旅行规划 Agent。涉及真实模型时单列预算与验证，缺模型授权时不冒充真实模型验证。
2. **约束冲突到显式调整**：把来源标记、未确认字段、失败日期、路途负担和修改后的版本对照串成可操作流程。保留未知，不自动提交或自动改条件。
3. **PC 工作台的信息层级**：表单按必填/逐日/可选约束整理，大屏地图与多日结果保留重点，执行状态和结果依据可定位；窄屏和键盘路径同步验证。布局变更以减少查找与重复输入为目标，不另做一次纯换皮。
4. **按职责整理组件与状态**：只在修改涉及的清晰边界提取规划表单、任务跟随和编辑状态，保留统一 transport 与现有恢复语义；不重写整个 App、不引入新的状态库或核心依赖升级。以完整需求→规划→编辑→断线恢复→保存对照流程验收。

B 包结束才判断是否需要更多业务字段或复杂 Agent。没有可靠来源的营业窗口、票价、库存与天气规则不混入此包。

## C：发布候选与后续双端接入

将 A/B 的最终代码与已有能力一起做一次综合验收：direct/MCP、Schema、账号隔离、取消/超时/限流、SSE/轮询、地图代理、编辑与版本、跨浏览器、性能、发布清单/密钥排除、归档启动；按改动风险重跑必要的本地 HTTPS/备份恢复，说明实际范围。

继续本地开发，保留每包独立回退点；最后上传 GitHub 的时机由用户明确发起，本计划不触发 push、PR 或发布。公网 DNS、真实域名、ACME、系统服务和异地备份等到服务器环境具备后验收，不再阻断本地可完成工作。

移动端是独立后续里程碑：确有 uni-app 工程后适配，若仍没有则新建薄客户端，接入已生成类型、`uni.request` transport、Bearer 登录及状态轮询；完成与 Web 同账号同后端的任务/行程/调整真机验证。原 Flutter 保留。没有完成真机测试前不把双端宣称为已验收。

复杂多 Agent、高级 Memory、全局最优求解、真实营业/预约/票价/库存作为更后续专题，分别以真实业务需求、可靠数据和评价方法为前提。
